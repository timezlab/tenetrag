## Q1 When do graphs help

**[R] Han et al. 2025, "RAG vs. GraphRAG: A Systematic Evaluation and Key Insights"** (Han, Ma, Wang, Shomer, Lei, Qi, Guo, Hua, Long, Liu, Aggarwal, Tang). arXiv 2502.11371 (v3, Mar 2026). preprint. Code: not stated on the abs page.
- Idea: unified protocol; compares vanilla RAG, KG-GraphRAG, Community-GraphRAG on QA and summarization; proposes Selection and Integration hybrids.
- Numbers (Llama 3.1-8B): NQ single-hop F1 RAG 64.78, KG-GraphRAG 50.27, Community-Local 63.01. MultiHop-RAG accuracy RAG 67.02, KG-GraphRAG 48.51, Community-Local 69.01. MultiHop-RAG temporal queries: RAG 30.70, Community-Local 50.60. Llama 70B: Integration hybrid +6.4% over best baseline, Selection +1.1%.
- Also reports LLM-judge position bias: reversing summary order flips judgments, sometimes to the opposite.
- Fit: C10 (graph does NOT beat RAG on single-hop; triplet-only KG context is worse than chunks), C2 (temporal queries gain from community/graph context, but from a low base), C8 (hybrid = graph + chunks).

**[R] Xiang et al. 2025, "When to use Graphs in RAG" (GraphRAG-Bench)** (Xiang, Wu, Zhang, Chen, Hong, Huang, Su). arXiv 2506.05690 (v latest Feb 2026). preprint. Code: github.com/GraphRAG-Bench/GraphRAG-Benchmark (license not checked).
- Four task levels: fact retrieval, complex reasoning, contextual summarization, creative generation.
- Novel-corpus accuracy: L1 fact retrieval Basic RAG 60.92 vs MS-GraphRAG 49.29; L2 reasoning RAG 42.93 vs HippoRAG2 53.38; L3 summarization RAG 51.30 vs MS-GraphRAG 64.40; L4 creative RAG 38.26 vs HippoRAG2 48.28.
- Prompt size: MS-GraphRAG global up to 4x10^4 tokens vs ~879 for vanilla RAG; LightRAG ~10^4; HippoRAG2 ~10^3.
- Fit: C10, C5 (token overhead). No temporal or aggregation-by-entity level.

**[R] Zeng et al. 2025, "How Significant Are the Real Performance Gains? An Unbiased Evaluation Framework for GraphRAG"** (Zeng, Luo, Lin, Jin, Wang, Fu, Yan, Jiang). arXiv 2506.06331. preprint. Abstract only read (PDF unreadable).
- Claims: existing evals suffer from unrelated questions and LLM-judge biases (position, length, trial); with graph-text-grounded question generation and bias controls, gains of 3 representative GraphRAG methods are "much more moderate than reported previously". Search snippet also says Edge et al. used LLM-judge with no reference answers.
- Fit: C10 direction — discount Microsoft-style win-rate headlines.

**[R] Microsoft Research, LazyGraphRAG blog (Jun 2025)** and BenchmarkQED (search snippet only). Not peer reviewed, vendor claims.
- Indexing cost "identical to vector RAG and 0.1% of full GraphRAG". Global queries: comparable to GraphRAG Global at >700x lower query cost; at 4% of global query cost beats all compared methods. Test: 100 synthetic queries (50 local, 50 global), 5,590 AP news articles, LLM-judge win rates. Weak evidence: one corpus, synthetic queries, LLM judge, vendor.
- BenchmarkQED compares against LightRAG, RAPTOR, TREX, vector RAG with 8k and 120k windows (snippet only; not read).

## Q2 Indexing cost
- **[R] KET-RAG** (Huang, Zhang, Xiao 2025), arXiv 2502.09304, preprint. LLM KG extraction only on "skeleton" key chunks, keyword-chunk bipartite graph for the rest. Reports comparable or better quality than MS GraphRAG at >10x lower indexing cost; up to +32.4% generation quality at ~20% lower cost. No code on abs page. Fit C5, C6 (tables-friendly). Single-group, LLM-judge-style generation metrics not verified.
- **[R] E2GraphRAG** (Zhao et al. 2025), arXiv 2505.24226. preprint. spaCy entity graph plus LLM summary tree, bidirectional entity-chunk index. Up to 10x faster indexing than GraphRAG, ~2x faster than RAPTOR; >100x retrieval speedup vs LightRAG; "competitive" quality. Code github.com/YiboZhao624/E-2GraphRAG. English-oriented spaCy; Vietnamese NER would need a different tagger. Fit C5, C6.
- **[R] MiniRAG** (Fan, Wang, Ren, Huang 2025), arXiv 2501.06713. Heterogeneous chunk-entity graph for small LMs; comparable quality with 25% of storage. Code HKUDS/MiniRAG. Fit: small-model extraction.
- **[R] NodeRAG** (Xu et al. 2025), arXiv 2504.11544. Heterogeneous node types, claims faster indexing and lower storage than GraphRAG and LightRAG. Code Terry-Xu-666/NodeRAG. Abstract-level evidence only.
- **[R] LazyGraphRAG** see Q1. Best cost-per-quality story, but defers LLM work to query time (latency, no persistent claim graph).
- [M] LightRAG variants, noun-phrase graphs (HippoRAG-style OpenIE alternatives), LinearRAG (arXiv 2510.10114, seen in search only) — not read.
- Takeaway: several independent methods (KET-RAG, E2, LazyGraphRAG) converge on "LLM only on a subset, cheap NLP elsewhere", but each is self-reported against MS GraphRAG, itself a weak, costly baseline. No head-to-head against well-tuned hybrid BM25+dense RAG.

## Q3 Retrieval innovations
- **[R] HippoRAG 2**, Gutiérrez, Shu, Qi, Zhou, Su, "From RAG to Memory", ICML 2025 (peer-reviewed). arXiv 2502.14802. Personalized PageRank over entity-passage graph with passage nodes and LLM recognition filter. Abstract: +7% on associative memory over SOTA embedding models, no loss on factual and sense-making. Code OSU-NLP-Group/HippoRAG. No GNN, no training; PPR is runnable on adjacency tables. GraphRAG-Bench shows it best on reasoning and creative tasks. Fit C1, C6, C4 (add nodes without retraining).
- **[R] PathRAG** (Chen et al. 2025), arXiv 2502.14902; flow-based path pruning, relational-path prompts; code BUPT-GAMMA/PathRAG; six datasets, LLM-judge on five dimensions (judge-only, same authors group as LightRAG lineage). Weak evidence.
- **[R] NodeRAG, MiniRAG** see Q2.
- [M, see follow-up for those since read] ToG / ToG-2, GraphReader (agentic graph exploration), StructRAG, G-Retriever (GNN + PCST; needs training), GFM-RAG (graph foundation model; needs training), RAPTOR, SiReRAG, HyperGraphRAG, ArchRAG, DRIFT, Dense X. Methods needing GNN or training (G-Retriever, GFM-RAG) conflict with a small SDK with no graph DB.

## Q4 Temporal
- **[R] Zep/Graphiti**, Rasmussen, Paliychuk, Beauvais, Ryan, Chalef, arXiv 2501.13956 (Jan 2025), preprint by vendor, code Graphiti (Apache-2.0, not re-checked). Bi-temporal edges (event time and ingestion time), invalidation of contradicted edges. DMR 94.8% vs MemGPT 93.4%; LongMemEval up to +18.5% accuracy with ~90% lower latency. Caveats: DMR is a weak benchmark; vendor-authored; see follow-up for the scalability critique. Domain is chat memory, not documents. Fit: C2 design pattern (valid_from/valid_to, supersede not overwrite) matches our need, but its destructive invalidation ("flag newest") must be softened to "return all versions". C4 cost risk.
- **[R] T-GRAG**, Li et al., arXiv 2508.01680 (Aug 2025), preprint. Temporal KG generator, temporal query decomposition, three-layer retriever. Benchmark Time-LongQA built by authors from corporate annual reports. Claims large gains; new self-built benchmark; code "public" (link not captured).
- **[R] DyG-RAG**, Sun et al., arXiv 2507.13396 (Jul 2025), preprint. Dynamic Event Units with temporal anchors, event graph, time-aware traversal, Time-CoT. Code RingBDStack/DyG-RAG. Fit: events with dates as retrieval unit matches meeting-minute decisions.
- [M] TimeR4, STAR-RAG (seen in search), IA-RAG (interval algebra, arXiv 2606.06044, snippet only). Not evaluated.
- Gap: no benchmark for "as-of date over edited documents with conflicting definitions". Han et al. temporal queries (MultiHop-RAG) are news-time comparisons, not versioned facts.

## Q5 KG construction quality
- **[R] EDC** Zhang and Soh, EMNLP 2024 main (peer-reviewed), arXiv 2404.03868. Extract open triples, define relations, canonicalize post hoc, with schema retriever. Beats prior on WebNLG, REBEL, Wiki-NRE in target-alignment and self-canonicalization. Fit C7: extract-then-canonicalize keeps verbatim text first.
- **[R] AutoSchemaKG**, arXiv 2505.23628, ACL 2026 (peer-reviewed per search listing). Schema induction jointly with extraction, conceptualization of entities and events; ATLAS 900M nodes, 5.9B edges from 50M docs; 95% semantic alignment with human schemas. Web-scale English; cost not read. Fit: schema induction for glossary-like entity types.
- Entity resolution and meeting extraction: see follow-up.

## What the evidence says
- Single-hop fact questions: vanilla (hybrid) RAG matches or beats graph methods (Han et al.; Xiang et al.: 60.9 vs 49.3). Triplet-only context hurts (48.5 vs 67.0 on MultiHop-RAG).
- Multi-hop and reasoning: graph methods win modestly (HippoRAG2 53.4 vs 42.9 on reasoning, Xiang et al.; Community-Local 69.0 vs 67.0 overall, Han et al.). Temporal subset gains larger (50.6 vs 30.7) but from a low base.
- Summarization and global sensemaking: graph community methods win (64.4 vs 51.3) at 40x-50x prompt tokens; LazyGraphRAG claims same quality cheaply (vendor, LLM judge).
- Hybrid (graph + chunks) is more robust than either alone (Han: +6.4%).
- Judge-based win rates are inflated by bias (Zeng et al.; Han et al.). Prefer reference-answer metrics.
- No paper tests entity-centric aggregation with provenance, as-of queries, or Vietnamese documents. Our criteria C1, C2, C3, C7 are extrapolated.

## Ranked concepts to adopt
1. Hybrid retrieval: chunks + graph context, never triples alone — evidence in two independent benchmarks.
2. Keep the chunk store as ground truth; entities and claims link to chunks (C3, C10).
3. Bi-temporal validity on facts (valid_from/valid_to, ingestion time), supersede-don't-delete, return all versions.
4. Event/claim units with dates as retrieval unit (DyG-RAG idea, Dense X propositions) — weakly evidenced.
5. PPR over an entity-chunk graph in tables (HippoRAG 2).
6. Selective LLM extraction plus cheap lexical linking for the rest (KET-RAG/E2).
7. Extract-then-canonicalize entity resolution (EDC), with per-language blocking.
8. Query routing between chunk-only and graph paths.
9. Lazy/query-time summaries instead of pre-built community reports.

## Hype or poorly evidenced
- Pre-built community summaries for entity-centric questions.
- Judge-only win-rate claims (original GraphRAG, LightRAG, PathRAG).
- Vendor memory benchmarks (Zep on DMR); self-built temporal benchmarks (T-GRAG).
- GNN or foundation-model retrievers (G-Retriever, GFM-RAG) [M].
- Cost-vs-MS-GraphRAG comparisons: no comparison to tuned hybrid RAG.

**1. MaGiX** — Nguyen Manh Hieu, Vu Lam Anh, Hung Pham Van, Nam Le Hai, Linh Ngo Van, Nguyen Thi Ngoc Diep, Thien Huu Nguyen. Findings of EMNLP 2025, pp. 5202-5219, DOI 10.18653/v1/2025.findings-emnlp.279. peer-reviewed (Findings). [R abstract only]
- Method (abstract): multi-granular cross-lingual KG with fine-grained attribute descriptions and cross-synonym edges; custom multilingual embedding trained with contrastive learning; graph reasoning plus semantic-aware reranking at retrieval. Five benchmarks, outperforms prior GRAG systems (GraphRAG, LightRAG, HippoRAG2 named as baselines class) on retrieval and generation.
- NOT verified: numbers, benchmark names, baselines table, code. My PDF extraction returned a description (NER entity-linking benchmarks, GPT-3.5 synonym generation at ~$0.08 per 1k entities, "project repository") that contradicts the abstract. Treat as fabricated and discarded. The ACL page does not link code. You need to read the PDF yourself (aclanthology.org/2025.findings-emnlp.279.pdf) before relying on it.
- Fit C7: only English-Vietnamese GRAG paper found. Trained embedding model implies a training step; code availability unknown. Label `single-paper`, numbers unread.

**2. post-graph-rag** — Chandan Rajah, "post-graph-rag: A PostgreSQL-Native Bi-Temporal Graph RAG Engine with Temporal Grounding at Synthesis", arXiv 2608.24921 (v3), Aug 2026. preprint, single author. [R via HTML extraction; abstract page agreed]. Code https://github.com/crajah/post-graph-rag, Apache-2.0 (per paper text).
- Schema: vertex tables documents, entities, communities (HNSW-indexed embeddings); edge tables relations, doc_mentions, community_members, community_children. Relations carry valid_from/valid_to (filled only when the text states periods) and t_created/t_expired (transaction time).
- Entity resolution: one vertex per (realm, space, lower(name)); canonical-name lookup then alias match; longer surface form wins; typed entities never overwritten by bare Concept stubs. Rule-based, no LLM matching, no multilingual note.
- Predicates: optional controlled vocabulary in the extraction prompt, extracted predicates snap by prefix match ("design" -> "designed"); vague predicates (relates_to, associated_with, see_also) rejected.
- Retrieval: bounded k-hop SQL expansion from vector-matched seeds (2 hops default), temporal predicates applied inside the walk so paths cannot pass through superseded edges. Updates and deletes recorded as expiry, not destructive.
- Temporal grounding at synthesis: slice stated in the prompt; abstract says temporal-reasoning score 0.496 -> 0.881 from this.
- Benchmarks: LongMemEval (500 q) 94.0% overall with gemini-3.6-flash answering and gemini-3.7-flash extraction; temporal reasoning 96.2%, multi-session 90.2%; comparison rows Zep (gpt-4o) 71.2%, full context 60.2%. ECT-QA (earnings calls, 6 companies x 16 quarters) 0.807 vs 0.599 TG-RAG, 0.406 LightRAG, 0.405 GraphRAG, "under that benchmark's own protocol" (published numbers from other papers).
- Strength of evidence: weak-to-moderate. Single author, preprint, "single runs per configuration" and "single run under one protocol" (the paper's own scope statement). Comparisons use different answering models than the baselines (newer Gemini vs gpt-4o), so the gap mixes model and architecture effects. Chat memory and transcripts, not minutes or definitions; English; no Vietnamese; no conflict-version benchmark. Value: design reference for the schema (very close to our storage design), not evidence of quality. Fit C2, C3, C6, C4.

**3. RAGSearch** — Fan, Xue, Liu, Tan, "Do We Still Need GraphRAG? Benchmarking RAG and GraphRAG for Agentic Search Systems", arXiv 2604.09666, preprint. Code https://github.com/FanDongzhe123/RAGSearch (license unchecked). [R abstract; PDF extraction partial]
- Datasets NQ, PopQA, TriviaQA, HotpotQA, MuSiQue, 2Wiki; agentic systems Search-o1, Search-R1, Graph-R1. Finding: agentic search substantially improves dense RAG and narrows the gap to GraphRAG, especially with RL-trained agents; PDF summary says dense RAG is "competitive or superior" under agentic search; GraphRAG keeps an edge on complex multi-hop and is more stable. Offline-cost numbers not obtained.
- Fit C10, C8: for agent-driven consumers (our case), multi-round retrieval over chunks recovers much of the graph benefit; graph value shifts to structured, provenance-bearing output rather than raw accuracy. Open-domain QA only, no enterprise or temporal data.

**4. Zep scalability critique** — Wu et al., "Memory in the LLM Era: Modular Architectures and Strategies in a Unified Framework", arXiv 2604.01707, preprint. [R HTML]
- Actual evidence is narrower than my first-pass snippet implied: a unified framework comparing memory methods on LoCoMo and LongMemEval; the rule is "if a method cannot finish in two days, we mark its result as '—'" on 8 A100 (80 GB) GPUs; Zep shows "—" for LongMemEval, with explanation in Appendix H "Memory Construction Cost of Zep", which I could not read. Measured construction cost as token consumption (proxy); text says Zep shows "poor token-cost scalability due to increasing memory update overheads". Zep retrieval latency 536.8 ms (no query-time LLM). Zep on LoCoMo (Qwen3.5-9B) F1 42.89, BLEU-1 36.94.
- Implication C4: entity resolution and edge invalidation against a growing graph make per-update cost grow with graph size. Does not show 100x volume claim (from snippet, unverified). `single-paper`, third-party, different hardware and local models than Zep's own setup.

**5. Practical GraphRAG** — Min, Bansal, Pan, Keshavarzi, Mathew, Kannan, "Towards Practical GraphRAG: Efficient Knowledge Graph Construction and Hybrid Retrieval at Scale", arXiv 2507.03226 (rev Dec 2025), preprint. [R abstract]
- Dependency-parse KG reaches 94% of LLM-based extraction quality (61.87% vs 65.83%) at far lower cost; hybrid retrieval fuses vector and graph traversal by RRF with separate embeddings for entities, chunks, relations; up to +15% and +4.35% over vector baselines on enterprise legacy-code-migration data, LLM-as-judge. Code not confirmed. Fit C5, C6, C7: a parser-based graph needs a Vietnamese dependency parser (not checked). Single-company, judge-based.

**6. DocuSearch** — Saragadam, Sharma, Pujari, arXiv 2609.01617 (Jun 2026), preprint. [R abstract] Vector (BGE-Large, weight 0.50) + BM25 FTS5 (0.35) + KG edge-table neighbour expansion (0.15) merged by RRF (k=60), cross-encoder rerank, MMR; per-chunk LLM grounding check. Telecom corpus: P@10 0.69 (+15 pts over dense-only), R@10 0.79 (+16), grounding 89.6% (+18.4). Dense-only is the baseline, so the BM25 and KG contributions are not separated here as far as read; no ablation seen. Fit C8, C6, C10 (supports hybrid lexical+dense). Industry preprint, own corpus.

**7a. RAPTOR** — Sarthi, Abdullah, Tuli, Khanna, Goldie, Manning, ICLR 2024 (per brief; page read showed arXiv 2401.18059, CC BY 4.0). Recursive embed-cluster-summarize tree. GPT-4 + RAPTOR gives +20% absolute on QuALITY. No GNN, no training. Summaries are generative, so figures are not verbatim; poor fit for versioned facts (re-clustering on edits). Code not checked.
**7b. Dense X Retrieval** — Chen, Wang, Chen, Yu, Ma, Zhao, Zhang, Yu, arXiv 2312.06648, EMNLP 2024 (per brief; page read showed only arXiv). Propositions (atomic self-contained factoids) as the retrieval unit improve retrieval and downstream QA over passages and sentences. Abstract gives no numbers. Fit C3, C2: propositions are rewrites by an LLM, so verbatim figures need the source span linked.

**8a. Think-on-Graph 2.0** — Ma, Xu, Jiang, Li, Qu, Yang, Mao, Guo, arXiv 2407.10805, preprint on the page read. Iterative retrieval alternating KG and document sources, training-free; SOTA on 6 of 7 datasets with GPT-3.5; Llama-2-13B raised to GPT-3.5 level. Code IDEA-FinAI/ToG-2. Needs an external KG such as Wikidata plus an LLM loop per query; costly at query time.
**8b. StructRAG** — Li et al. (Han, Sun, Li labs), arXiv 2410.08815, preprint on the page read. Router picks a structure type (table, graph, algorithm, catalogue, chunk) per question and builds it at inference time. SOTA on knowledge-intensive reasoning benchmarks per abstract; no numbers read. Fit C1, C8: table-structured aggregation at query time suggests a SQL-style output for entity-centric questions. Needs a trained router (DPO) per abstract-level memory; unverified.

**9. DRIFT search** — Microsoft Research blog. Primer over community reports produces initial answer plus follow-up questions; follow-up local searches iterate; results ranked. On 5,000+ AP articles with 50 local queries, LLM-judge win rates vs Local Search 78% (comprehensiveness) and 81% (diversity). Caveats stated: one dataset, two iterations hard-coded, naive map-reduce aggregation. Vendor blog, LLM judge, no ground truth. Depends on community reports (costly index). Weak evidence.

**10. Entity resolution and meeting extraction** — Searches only; no primary paper read.
- ER snippets: LLM pairwise matchers reach F1 up to 98.95% vs 91.33% for rule matchers on benchmarks (near human label consistency); retriever-then-LLM matching is the common KG pattern; LLMs fail mostly on cross-script transliteration and identifier/date inconsistencies; effort best spent on blocking, clustering and uncertainty-aware review (arXiv 2603.11051 and a CEUR paper appeared in the search; I did not open them). Also iText2KG (arXiv 2409.03284) for incremental KG building (not read). `estimate`. No Vietnamese or diacritics-specific ER evidence; diacritic stripping vs "Việt/Viet" variants is an unaddressed risk.
- Meeting decisions: the AMI DecisionDetector line (Edinburgh) is classical dialogue-act work on transcripts, not minutes. No 2024-2025 benchmark for decision/action-item extraction from written minutes found; MeetingBank not opened. Gap: no error-rate data for our document type. Recommend building a small golden set from public synthetic minutes.

### Updated judgment
- Hybrid fusion (BM25 + dense + graph expansion via RRF) has independent industry support (DocuSearch, Practical GraphRAG), but both are judge- or own-corpus evidence.
- Agentic multi-round chunk retrieval narrows the graph gap (RAGSearch), which reinforces: sell structured provenance output, not accuracy over RAG.
- post-graph-rag validates the table schema and as-of SQL traversal design but its quality numbers are weak evidence; adopt the schema ideas (valid time vs transaction time, snap-to-vocabulary predicates, drop vague predicates, temporal predicate inside the walk) not the scores.
- Zep-style per-update resolution cost scaling is a documented risk; batch ER and blocking should be designed in.
- MaGiX numbers remain unverified and are the top remaining item: read the PDF directly.
