## How it works

### 1. GraphRAG module (v0.27.2, `rag/graphrag/`)
- **Variants** [source `general/index.py:118-137`]. `method` is `light` (default), `general` or `ner`.
  - `general` is the MS GraphRAG prompt (MIT header, `general/graph_prompt.py`).
  - `light` is the LightRAG prompt (MIT header, `light/graph_prompt.py`). It adds relationship keywords and content keywords.
  - `ner` uses spaCy, with no LLM for extraction (`ner/ner_extractor.py`). Its model map covers en, zh, de, fr, es, pt and ja, and **there is no Vietnamese** model (`_MODEL_MAP`, lines 41-49).
- **Extraction format.** Tuple records `("entity"<|>name<|>type<|>desc)` and `("relationship"<|>src<|>tgt<|>desc<|>strength)`. Delimiters are `<|>`, `##` and `<|COMPLETE|>`. Default entity types are organization, person, geo, event, category [source: `general/extractor.py:42-44`].
- **Chunk batching.** Chunks are concatenated into ~4096-token batches before extraction (`DEFAULT_GRAPHRAG_BATCH_CHUNK_TOKEN_SIZE`, `index.py:63`; `load_doc_chunks`, line ~320). So `source_id` is the **doc id, not a chunk id**. Chunk-level provenance is lost.
- **Gleaning.** `ENTITY_EXTRACTION_MAX_GLEANINGS = 2`. Each round sends `CONTINUE_PROMPT` and then a Y/N `LOOP_PROMPT` (`general/graph_extractor.py:100-125`).
- **Merge within a document** (`Extractor._merge_nodes`/`_merge_edges`, `extractor.py:~225-262`). The most common type wins. Descriptions are joined with `<SEP>` and deduplicated. Edge weights are summed.
  - An LLM summary runs only if there are more than 12 descriptions. Before that check the text is truncated to 512 tokens, so an over-long list is silently cut.
  - Edges are keyed by the sorted pair, so they are **undirected**.
  - Extracted relations are dropped if an endpoint is missing or the description looks negative or misattributed (`_relationship_looks_valid`).
- **Entity resolution** (`entity_resolution.py`):
  - **Blocking.** Pairs are formed only within the same `entity_type`. A pair is kept if at least one node is new, and `is_similarity` passes.
  - `is_similarity` rejects any pair whose character-2-gram symmetric difference contains a digit. For English, it requires Levenshtein distance ≤ min(len)//2 (rapidfuzz). For non-English, it uses character-set overlap ≥ 0.8, or more than 1 shared character when max length is under 4.
  - **LLM confirmation.** Batches of 100 pairs per prompt, with 5 concurrent requests. The answer format is `For question <|>i<|>, &&yes&&`.
  - **Merge.** Connected components of the "yes" pairs are merged into node[0]. Descriptions are concatenated and re-summarized, and edges are rewired. Then PageRank is recomputed.
  - The character-set test is a Chinese heuristic. It would over-match Vietnamese strings that share diacritic letters, and it ignores syllable structure [inferred].
  - The whole pair space is O(n²) per type before filtering, and combinations are enumerated in memory [source: `itertools.combinations`].
- **Community detection.** `graspologic.partition.hierarchical_leiden`, `max_cluster_size=12`, fixed seed, on the largest connected component (`general/leiden.py`). graspologic is MIT [source: `gh api license`]. It is pinned to an InfiniFlow fork on gitee (`pyproject.toml:56`).
- **Community reports.** MS GraphRAG's `COMMUNITY_REPORT_PROMPT`, returning JSON with title, summary, rating, and findings carrying `[Data: ...]` references. Communities with fewer than 2 entities are skipped. Edges are capped at 10,000 per community.
- **Persistence.** There is no graph DB. Everything is stored as **chunks in the doc store** (ES, OpenSearch, Infinity, plus GaussDB, OceanBase and SereneDB mappings). The discriminator field is `knowledge_graph_kwd` (`utils.py:414-500, 550-740`):
  - `graph`: the whole NetworkX graph as `node_link_data` JSON in one chunk.
  - `subgraph`: one JSON blob per document, with `source_id=[doc_id]`.
  - `entity`: `entity_kwd`, `entity_type_kwd`, `rank_flt` (PageRank), `n_hop_with_weight` (a precomputed JSON list of 2-hop paths), `source_id` list, a vector `q_<dim>_vec` of the **entity name only**, and the description in `content_with_weight`.
  - `relation`: `from_entity_kwd`, `to_entity_kwd`, `weight_int`, with an embedding of `"A->B: description"`.
  - `community_report`: `entities_kwd` and `weight_flt`.
  - `ty2ents`: type to sample entities, used for query rewrite.
  - There are **no time or validity fields** on any of them.

### 2. Incremental behaviour
- **Add** [source: `general/index.py:256-640`]. This is a KB-level batch job, not automatic per document. The notes at line 717 say the automatic incremental build was replaced by "manual batch building". The steps:
  1. Build a per-doc subgraph and save it as a `subgraph` chunk. It is skipped if one already exists (checkpoint).
  2. Take the Redis lock `graphrag_task_{kb_id}` (timeout 1200s).
  3. Load the global graph with `get_graph`, then `graph_merge`: descriptions are concatenated with `<SEP>`, `source_id` lists extended, and weights summed.
  4. Recompute PageRank and run `set_graph`.
  5. Run resolution and then community, each only if the phase marker is missing. A merge **resets both markers**, so any new doc triggers full community regeneration.
- **`set_graph` is delete-then-insert.** It builds all new chunks first, **deletes every `graph` and `subgraph` chunk for the KB**, deletes changed entities and edges, then re-inserts (`utils.py:690-740`). Only entities and relations touched by the change are re-embedded.
- **Delete** (`api/db/services/document_service.py:~548-570`). It does not rebuild the graph.
  - It runs a doc-store update `remove source_id=doc.id` on entity, relation, graph, subgraph and community_report rows.
  - It marks `graph.removed_kwd=Y`, then deletes rows with no `source_id` left.
  - **Descriptions are not rewritten.** Text contributed by the deleted doc stays in surviving entities, merged into `<SEP>` descriptions and summaries. Community reports are not regenerated [inferred from the code path: no LLM or description edit on delete]. The step is wrapped as non-critical, so failures are only logged.
  - Edit is delete plus re-add [inferred]. No per-fact validity exists to support anything better.
- **`rebuild_graph`** (`utils.py:869`) can recompose the global graph from subgraph chunks. I found no caller in the Python tree outside `structure.py`.
- **Concurrency.** One Redis distributed lock per KB serializes merge and post-merge. Cancel checks run throughout. Retry, timeout and per-phase checkpoints live in Redis (`checkpoints.py`). Community checkpoints are keyed by the sorted node set, **but are cleaned up after each run**, so a later run recomputes all communities [source: `cleanup_checkpoints`, `index.py:~1010`].

### 3. KG retrieval (`rag/graphrag/search.py`, `KGSearch.retrieval`)
- **Rewrite.** An LLM is given the question plus the type-to-sample-entities pool (`ty2ents`). It returns `answer_type_keywords` (at most 3) and `entities_from_query` (the first 5 are used). On failure, the whole question is used as the entity string (`query_rewrite`, lines 38-60). This prompt is the MiniRAG `minirag_query2kwd`.
- **Candidate sets.**
  - Entities by dense similarity on the entity name embedding, threshold 0.3, N=56.
  - Entities by type, sorted by PageRank.
  - Relations by dense similarity of the question, threshold 0.3.
  - 2-hop paths come from the stored `n_hop_with_weight`. No query-time traversal is done. Each hop adds `sim/(2+i)`.
- **Scoring.** `P(E|Q) = pagerank × sim`. Entities that also appear in the type set get ×2. A relation's score is multiplied by `(1 + n_hop_sim + endpoint_in_types)`. The final sort key is `sim × pagerank`.
- **Output.** The result is **one pseudo-chunk** titled "Related content in Knowledge Graph" (`docnm_kwd`, `similarity=1.0`, empty `doc_id`). Its text is CSV tables, "---- Entities ----" and "---- Relations ----", followed by "---- Community Report ----". Defaults are 6 entities, 6 relations and 1 community report.
  - Community reports are selected by `entities_kwd` containing the top entities, sorted by `weight_flt`.
  - Each carries the report plus "Evidences" text.
- **Token budget.** `max_token=8196`, decremented per row. Entities and relations stop when the budget goes negative. The community loop **decrements but never checks** the budget (`_community_retrieval_`), so the report can overshoot [source].
- **Limits.**
  - Entities and relations carry **no doc or chunk references** in the output, so no provenance reaches the agent.
  - The KG block is merged with normal chunk results and uses vector similarity only [docs: `notes_and_faqs.md:45`].

### 4. RAPTOR
- **Legacy.** `rag/raptor.py` is absent at v0.27.2. The tree builder is `rag/advanced_rag/knowlege_compile/raptor.py`, with orchestration in `rag/svr/task_executor_refactor/raptor_service.py`.
- **Clustering.** **1-D watershed over adjacent-chunk cosine similarity**, not UMAP/GMM [source: `_get_clusters_ahc`, lines 120-185]. Only neighbouring embeddings in document order are compared. The split threshold is the 30th percentile of adjacent similarities, capped by `clustering_ratio` 0.5. Layers are summarized recursively, each summary carries a title, and the tree is materialized with parent-child links.
- **Config** [source: `api/utils/validation_utils.py:346-380`]: `max_token` 512 to 2048, `max_cluster` 64, `scope` file or dataset, and `auto_disable_for_structured_data=True` (skips xlsx/csv). The default prompt says "without inventing facts or changing numbers".
- **Cost warning.** The docs list RAPTOR first among things to switch off to accelerate indexing [docs: `accelerate_doc_indexing.mdx:17`]. I found no explicit "when to use" guidance in the docs I read.
- **rc1.** `internal/ingestion/component/knowledge_compiler/tree/raptor.go` and `tree/claims.go` implement the successor (a Tree variant plus claim extraction with evidence).

### 5. Other retrieval features
- **Hybrid.** Weighted sum of full-text and dense. Default `vector_similarity_weight=0.3`, so 0.7 term and 0.3 vector (`rag/nlp/search.py:36-42, 254, 601-602`). The docs show the formula `25.17×0.7 + 36.49×0.3`. Default similarity threshold is 0.2. The Infinity path normalizes before fusion.
- **Rerank.** An optional rerank model (`rerank_by_model`). Candidates are 64 (`rerank_candidates_count`), and pagination is disallowed once reranking is on (lines 593-635). Without a model, hybrid similarity is recomputed locally from the term and vector scores. Tag-feature scores and PageRank are added to the score.
- **TOC.** A per-doc TOC is stored as a chunk with `toc_kwd="toc"`. `retrieval_by_toc` picks the best-scoring doc and asks an LLM to select relevant TOC entries, then adds those chunks (`search.py:905-966`). It uses only the **top single document** and needs a chat model at query time.
- **Parent/child.** `children_delimiter` splits chunks into children. The parent text is stored as `mom_with_weight`. Retrieval hits children, then `retrieval_by_children` swaps in the parent text with the mean child similarity (`search.py:968-1010`, `rag/nlp/__init__.py:477`).
- **Tags.** `tag` chunk template (`rag/app/tag.py`) plus `tag_kwd`/`tag_feas`. Query tags yield a rank-feature score (`_tag_feature_scores`). This is a label-weighted boost, not a filter.
- **Per-chunk LLM extras** (`task_executor.py:483-535`): `keyword_extraction` (auto_keywords), `question_proposal` (auto_questions), `content_tagging`, `gen_metadata`, `run_toc_from_text`. Each is a per-chunk LLM call at index time. The keywords and questions are indexed as `important_kwd` and `question_kwd`.
- **Cross-language.** Optional: an LLM translates the query into the target languages and concatenates the results (`cross_languages` in `rag/prompts/generator.py:292`; use at `chunk_api.py:382-486`). Failure falls back to the original query. This helps cross-lingual lookup but needs a chat call per query.
- **Metadata filters.** `meta_filter.md` prompts an LLM to produce `{conditions, logic}` with operators `= ≠ > < ≥ ≤ contains in ...`. Date-range handling is a prompt rule ("July" becomes `≥ YYYY-07-01, < YYYY-08-01`). Filtering applies to **document metadata, not facts** [source: prompt text]. No bitemporal handling exists.

### 6. DeepDoc / parsing
- **Models.** `deepdoc/vision/` holds OCR, `layout_recognizer.py` and `table_structure_recognizer.py`. The models download from HF repo `InfiniFlow/deepdoc` (ONNX, [source: `snapshot_download(repo_id="InfiniFlow/deepdoc")`]). Model license **not verified**.
- **Layout and tables.** Per `deepdoc/README.md`: 10 layout classes, 5 TSR labels, and table auto-rotation (v0.2x). TSR output is reassembled into sentences for the LLM [docs].
- **Parsers.** `deepdoc/parser/` has docx, excel, ppt, pdf, markdown, html, epub and json. Integrations: **MinerU** (`mineru_parser.py`, Apache-2.0 header, includes a `"Vietnamese": "latin"` language map), **Docling** (`docling_parser.py`), PaddleOCR, Mistral, MonkeyOCR, OpenDataLoader, SoMark and TCADP.
- **Chunk templates** (`rag/app/`): naive (general), book, laws, manual, one, paper, presentation, qa, resume, table, picture, audio, email, tag.
- **rc1 note.** "DeepDoc currently supports CPU environments only" [docs: release body].

### 7. Multilingual
- **Tokenizer.** `rag/nlp/rag_tokenizer.py` subclasses `infinity.rag_tokenizer.RagTokenizer` (infinity is Apache-2.0). When the doc engine is Infinity, `tokenize` returns the line unchanged and the engine's analyzers run (`rag-coarse`, `rag-fine`, `whitespace-#`, `conf/infinity_mapping.json:10-34`). With ES or OpenSearch, the tokenizer's Chinese segmentation path runs.
- **Chinese specifics** [source]: traditional-to-simplified conversion and full-width to half-width in `query.py:54`, synonym dictionaries, and term-weight files.
- **Vietnamese.** I found **no Vietnamese-specific tokenizer, stop-word, diacritic or segmentation code**. The only mentions are the MinerU language map and the spaCy list, which lacks `vi`. Vietnamese text falls through the Latin or whitespace path, so multi-syllable words are split into syllables. This works as syllable n-gram-like matching but with no word segmenter [inferred; the infinity tokenizer source was not read].
- **Entity-resolution thresholds** are tuned for English (Levenshtein) and Chinese (character sets), neither of which fits Vietnamese.
- **Prompts** say "in language of 'Text'", so extraction preserves the source language. Resolution prompts are English with English examples.

## Fit per criterion
- **C1 entity aggregation:** Partial. Entities are merged globally by exact name plus LLM-confirmed fuzzy pairs. Descriptions are an unstructured `<SEP>` blob and are summarized only above 12 items. Retrieval returns top-6 entities and relations.
- **C2 time / versions:** **None** in classic GraphRAG. Conflicting definitions are merged into one description, and the LLM summary prompt says to "resolve contradictions" (`SUMMARIZE_DESCRIPTIONS_PROMPT`), which is the opposite of what we need. rc1 has a Timeline kind, but it is template-driven chain ordering, not validity intervals.
- **C3 provenance:** Weak. Entities and relations carry `source_id=[doc_id]` only (after batching, no chunk ids), and the KG output omits it. rc1's evidence quotes with located spans are stronger (see Borrow).
- **C4 incremental:** Add means merge plus **full community regeneration** and full graph chunk rewrite. Delete leaves stale description text. A per-KB lock serializes everything.
- **C5 cost/latency:** High indexing cost (extraction with up to 2 gleanings, LLM pair resolution, a report per community). Query needs one LLM rewrite call plus several vector searches. The docs state KG retrieval "significantly increases" response time.
- **C6 relational fit:** Good. It maps to flat rows with typed discriminator columns, so it ports directly to Postgres or Delta. Precomputed `n_hop_with_weight` avoids recursive CTEs.
- **C7 multilingual/ER:** Chinese is first-class, Vietnamese is not covered. ER thresholds are English/Chinese-specific. Aliases are handled only by blocking plus LLM merge, with no alias table.
- **C8 context-only output:** One concatenated CSV string in a fake chunk. It is not structured, so it is not agent-friendly.
- **C9 license/maintenance:** Apache-2.0 and very active, but the module we would borrow is deprecated and its Python source was deleted in the rc1 tree. The graspologic fork (MIT) is pinned to gitee.
- **C10 vs vector RAG:** I found **no published evidence** in the repo that KG beats plain retrieval. The docs only warn about cost. Parent-child, TOC and tag boosts are hybrid-retrieval tricks, not graph evidence.

## Pitfalls
| Pitfall | Evidence | Our rule |
|---|---|---|
| Doc id as the only provenance, because chunks are batched into ~4096 tokens | `index.py:63, 320-345`; `ent["source_id"] = [doc_id]` | Extract per chunk, or keep chunk ids per extracted record. |
| Contradictory descriptions are summarized away | `SUMMARIZE_DESCRIPTIONS_PROMPT` ("resolve the contradictions") | Never merge conflicting versions into prose. Keep one claim row per statement with date and source. |
| Descriptions truncated to 512 tokens before the over-12 check | `extractor.py:_handle_entity_relation_summary` | Avoid lossy concatenate-truncate. Store claims individually. |
| Delete leaves stale text in merged descriptions | `document_service.py:~558-568` | Derive descriptions from claim rows so a delete is a row delete. |
| Any added doc invalidates and regenerates all communities | phase markers reset at `index.py:526-530`; checkpoints cleaned after run | If we add communities, regenerate only touched ones by hash. |
| Global delete-and-reinsert of the graph chunks | `utils.py:700-706` | Use row-level upserts. |
| Undirected edges (sorted pair key) lose direction ("A owns B") | `extractor.py` `tuple(sorted(k))` | Keep direction and predicate type. Ownership questions need it. |
| ER heuristics tuned for English and Chinese | `entity_resolution.py:is_similarity` | Design Vietnamese-aware blocking (diacritic-folded, syllable-token overlap, alias table) and test it on a golden set. |
| KG block returned as CSV text in a fake chunk without provenance | `search.py:retrieval` return value | Return structured records (entity, claim, chunk id, doc id, date). |
| Community budget not enforced | `search.py:_community_retrieval_` | Enforce token budgets on every section. |
| Cost blow-ups (a $200 / 36 h report) | issue #7957 | Show a cost estimate before indexing and set hard caps on calls per document. |
| Upstream abandoned the pipeline | `release_notes.md:94-95` | Treat it as design reference only. Do not track upstream. |
| Single-doc TOC retrieval needs an LLM at query time | `search.py:905-966` | Use a precomputed outline as data, not a query-time LLM call. |

## Verdict
RAGFlow's classic GraphRAG is a port of MS GraphRAG (prompts, Leiden, community reports) and LightRAG (prompts), with NetworkX as the engine and the doc store as a bag of chunks. Architecturally it adds nothing for time, validity or conflicting versions, and it gives worse provenance than we need, so we should not copy its schema or retrieval. The most useful parts are operational: per-document subgraph checkpoints, build-then-swap writes, hash-keyed checkpoints and ER blocking with a digit guard. The one idea that is better than what we planned to take from MS GraphRAG or LightRAG is the rc1 evidence gate: every extracted item carries a quote that is verified by locating it in the cited chunk, with soft or hard rejection and byte-aligned spans. That directly serves "figures verbatim with time and source". Beyond that, RAGFlow's current direction (template-defined schemas, Timeline kind, LLM merge decisions with a 0.99 similarity threshold) is promising, but it is a new Go codebase and we have only read it, not tested it.

## Follow-up: Knowledge Compilation (rc1)

### 1. Concept and pipeline
- **"Compile" means** an LLM turns each document's chunks into typed "knowledge artifacts" chosen by a *template*. Artifacts are stored as extra rows in the same doc store as chunks. [docs: `docs/guides/knowledge_compilation/overview.md`]
- **Pipeline shape:** Parser, Chunker, **Compiler**, Indexer, where Compiler is one component named "Compiler" (`K/component.go:~50`) [source]. Per document it resolves a template id or template-group id (`common/types.go` `ParseParam`: `compilation_template_id` or `compilation_template_group_id`, one required) and picks a variant from the template `kind` (`KindToVariant`, `types.go:~185`) [source].
- **Kinds and variants** [source `KindToVariant`]:
  - `tree` maps to the tree variant (`K/tree/`, RAPTOR-like plus claims).
  - `mind_map` maps to mindmap (`K/mindmap/`).
  - `wiki` maps to wiki (`K/wiki/`, a MAP, REDUCE, PLAN, REFINE pipeline).
  - `page_index`, `session_essence`, `session_graph`, `timeline`, `knowledge_graph` (alias `graph`) all map to **structure** (`K/structure/`, a two-stage entity then relation extraction). So **Graph, PageIndex and Timeline are the same engine with different YAML**. The kind decides the task label and post-processing.
- **Template definition.** Built-ins are YAML in `api/db/init_data/compilation_templates/` (`knowledge_graph`, `timeline`, `page_index`, `tree`, `mind_map`, `wiki`, `session_essence`, `session_graph`, plus `wiki/{brand,engineering,general,market,product,user_interview}.yaml`) [source]. They are seeded into the MySQL table `compilation_template` (`id, tenant_id, group_id, name, kind, config JSON, is_builtin, status`; `internal/entity/compilation_template.go`) [source]. Users can clone and edit them in the UI [docs]. Config is per template, not per dataset. A dataset gets it by attaching a pipeline whose Compiler node names the template.
- **Template fields** (`structure/prompt.go` `HypergraphPrompts`) [source]:
  - `entity.fields[]` (`type`, `description`, `rule`) and `relation.fields[]`.
  - `global_rules` and `rechunk_rules`.
  - `guideline.{target, rules_for_entities, rules_for_relations, rules_for_time}` (the legacy shape).
  - `output_fields[]` for extra keys such as `evidence`.
  - `options.observation_time`.
- **Stages for structure** (`structure/structure.go` `Run`) [source]:
  1. Pack chunks into batches by model window (50% utilization).
  2. MAP: per batch, an entity call and then a relation call (relations may only reference the stage-1 entities).
  3. Evidence gate.
  4. Embed the rows.
  5. In-document dedup.
  6. Chain validation for list/timeline.
  7. Emit entity and relation rows.
  - Extraction uses temperature 0.1 with thinking disabled.
- **Dataset level** (`internal/ingestion/knowledge_compile/`): a durable MySQL backlog plus NATS wake-ups. One worker claims a KB batch, then merges doc-level rows (`available_int=0`, `doc_id=<doc>`) into dataset-level rows (`available_int=1`, `doc_id=<kb>`, `source_doc_ids`) (`event.go`, `writer.go`, `consumer.go:514-810`) [source].

### 2. Data model per kind
- **Row storage** [source: `conf/infinity_mapping.json:12-80`]. Compiled rows are chunk-table rows. Discriminators and fields:
  - `compile_kwd`, `scope_kwd` (doc or dataset), `entity_type_kwd`, `name_kwd`, `mention_count_int`.
  - `from_entity_kwd`, `to_entity_kwd`, `source_chunk_ids` (json), `source_doc_ids` (json), `source_chunk_hashes`.
  - `content_with_weight` (payload JSON), plus `q_<dim>_vec`.
  - `compilation_template_kind_kwd` and `compilation_template_ids` are also stamped (`types.go`, `consumer.go`).
  - **No date, validity or supersedes column exists in the mapping.**
- **Entity row** (`structure/compile.go` `buildRows`) [source]. The payload JSON is whatever the template asked the LLM for (`type`, `name`, `description`, `source_chunk_ids`, optional `evidence`). Meta adds `name`, `entity_type`, `description`, `mention_count`. The id is `StableRowID(content, doc_id, template_id)`. The embedding is of the concatenated payload values.
- **Relation row.** Same, with `from`, `to` and `relation_type`. Self-loops are dropped. Relation direction is kept (`from`/`to` are ordered).
- **Timeline.** An event is two entity rows (`type: timestamp` and `type: event`) joined by `ordered` relations (`timeline.yaml`). The date is a **free-text `name`**, ISO preferred, and **no date type, interval or validity exists** [source: `timeline.yaml`].
- **Claims.** These exist in three places:
  - Tree: `tree/claims.go` `Claim{name, description, type, source_chunk_ids, evidence[]}`.
  - PageIndex: `title` and `claim` entity types, with `output_fields: evidence` (`page_index.yaml`).
  - Wiki: `claims[] {statement, subject, confidence, source_chunk_ids}` plus `entities[] {name, type, aliases[], source_chunk_ids}` and `concepts[] {term, definition_excerpt}` (`wiki/wiki.go:~120-135`).
- **Evidence record** `{quote, chunk_id, start, end}` is **byte offsets into the cited chunk text**, stored inside the payload JSON (`EvidenceRef`, `tree/claims.go:~175`) [source]. The default Graph and Timeline YAMLs do **not** request `evidence`. Only `page_index.yaml` and the Tree claim prompt do [source: grep of all YAMLs; `RelationExpectsEvidence`].
- **Chunk and doc ids.** `source_chunk_ids` is the model's pick filtered to the batch. If the model returns none valid, **all batch ids are used** (`payloadChunkIDs`, `compile.go:~110`) [source], so provenance can silently widen.
- **Tree** rows are summary nodes with `ParentID`, and level-0 nodes carry `source_chunk_ids`. Clustering is the watershed method already described.

### 3. Merge and dedupe
- **In-document** (`structure/merge.go`) [source]:
  - **Same normalized name** (lowercase, whitespace-collapsed) for entities merges **with no LLM and no similarity test**. Descriptions are joined with `\n` if different, aliases are unioned, and the type prefers the non-"other" one (`mergeEntitiesByName`).
  - Otherwise the candidate is the nearest stored row. **Only if cosine ≥ `SimilarityThreshold` (default 0.99, `types.go` Defaults)** does the LLM judge `{"duplicated", "merged"}` (`mergeDecisionInstruction`, batched). At 0.99, only near-identical embedded text reaches the judge, so alias merging by this path is rare [inferred].
  - Relations are grouped by `(from, to)` endpoints before comparing.
- **Merge prompt** says "If fields conflict, use your best judgment to pick the more detailed or recent-looking value" (`mergeSystemPrompt`) [source]. So an LLM-merged conflict is **resolved to one value, not kept as two**. For relations the endpoints are forced back to the existing row's values.
- **Aliases.** An LLM merge records `alias→canonical`, and relation endpoints are then rewritten through that map (`RewriteRelations`, `resolveAlias`) [source]. Wiki entities carry an explicit `aliases[]` list. There is no alias table, no language-aware matching, and no confirmation step beyond the judge.
- **Dataset level.** For structure kinds (`consumer.go:1565-1700`) rows are bucketed deterministically by `(template, lowercase name, compile kind)`, and relations by `(template, from, type, to, kind)`. **No LLM and no threshold.** Descriptions are concatenated with `\n`, `source_doc_ids` and `source_chunk_ids` are unioned, mention counts are summed, and vectors are averaged [source]. So **conflicting definitions of the same name end up as separate lines in one description, with doc ids, but no per-line date, source or "newest" marker**.
- **Wiki and topic pages** use KNN (`mergeThreshold: 0.85`, `consumer.go:94`) plus an LLM route decision.

### 4. Evidence gate
- **Locate** (`structure/evidence.go` `locateEvidence`, `tree/claims.go` `LocateEvidence`, identical) [source]:
  - Collapse runs of space, tab, CR and LF to one space in both quote and chunk text. Nothing else is normalized: no case folding, no Unicode normalization, no punctuation stripping.
  - Then `strings.Index` for an **exact substring**. There is **no fuzzy matching**.
  - A byte-aligned map returns offsets into the original text. A bug where rune-indexed maps misplaced CJK offsets is documented as fixed.
- **Which chunk.** If the entry cites a chunk id that exists, only that chunk is searched. If the id is missing or unknown, all batch chunks are scanned in sorted order.
- **Per payload.** Quotes that fail are dropped. If at least one survives, `evidence` is replaced by the verified list `{quote, chunk_id, start, end}` (note: `chunk_id` is rewritten to where it was actually found).
- **Soft vs hard (default soft).** When no quote is verified, soft **keeps the payload and deletes `evidence`**. Hard **drops the payload**. A payload with **no `evidence` at all passes through ungated**. Rejection counts are logged only [source].
- **Tree claims** (`ValidateClaims`): additionally a claim that neither the model nor its evidence can attribute to a chunk is dropped. The design comment says soft is the default because enumeration and multi-hop questions "degrade badly when facts are discarded" [source: `claims.go:~30`].
- **Scope limits.** Relations are gated only if the template declares `evidence` in `output_fields`. Entities are gated whenever they carry `evidence`. The Tree prompt requires quotes under 240 characters and preserves numbers, units and dates, and for tables it requires raw row text.

### 5. Timeline kind
- **Dating is LLM-by-prompt.** `timeline.yaml` instructs: prefer ISO 8601 or a normalized form, **convert relative expressions to absolute "when the context allows", otherwise keep the original expression**, `-1` if no time exists [source].
- **No resolution anchor.** There is a `{observation_time}` placeholder in `rules_for_time`, defaulting to `time.Now()` when unset (`prompt.go:HypergraphPrompts`). No built-in YAML uses `rules_for_time`, so **document date is not supplied** to the model [source: grep]. Relative dates are resolved with whatever the chunk text contains.
- **Ordering.** `validateAndCorrectChain` forces list/timeline relations into a strict linear chain with LLM correction that fails open, and `dropIsolatedTimelineEntities` removes entities with no surviving relation (`structure.go:228-247`) [source]. This is **source-order chaining, not date sorting** [inferred; the chain follows "source order as tie-breaker"].
- **Query.** There is no timeline-specific tool. The agent's compiled expansion lists `timeline` as one entity-kind and does a 1-hop expansion (`tool_compiled_expansion.go:~100`). `docs` say Timeline suits "historical materials, project records, event tracking" [docs]. Date-range queries are therefore not supported structurally [inferred].

### 6. Incremental behaviour
- **Add or re-parse.** A doc finishing the pipeline appends `doc_completed` to the KB backlog (`event.go`). A claimed worker merges this doc's rows into dataset rows under a per-dataset write lock with claim-token fencing (`consumer.go:296`). The last event per doc wins (completion vs deletion) [source].
- **Delete.** A worker deletes the doc-level rows, then **strips the doc id from `source_doc_ids` of dataset rows and deletes rows left with no source** (`StripMergedSources`, `DeleteStructureForDocs`) [source]. The strip rewrites only the source array. **Folded descriptions are not re-derived**, so a surviving merged row keeps text contributed by the deleted doc [inferred from the code; it only updates `source_doc_ids`].
- **Wiki** is better: it has a content-hash-keyed MAP cache per chunk (`wiki_map_cache.go`, `runVersionedMap`), a stored active state per doc, a contribution diff (`prepareWikiContributionDiff`), and affected-page selection, so unchanged chunks are not re-extracted and only affected pages are rewritten [source].
- **Edit** is re-parse, then the same completed path [inferred]. Structure and tree have no chunk-level cache found.
- **Updates are manual in the UI**: added or removed docs show an "Update" button, and template edits apply only on recompile [docs: `apply_knowledge_compilation_template.md:89`, `faq.md:39`].
- **Full rebuild** (`RebuildDataset`) clears and republishes all docs. `incremental` and `rewrite` modes currently take the same path [source: `consumer.go:325`].

### 7. Retrieval over compiled knowledge
- **Both fixed and agentic.** The agentic runtime (`internal/rag/agentic-rag/runtime/`) executes tool names `retrieve`/`search_chunks`, `metadata_search`, `navigate_tree`, `navigate_structure`, `list_chunks`, `fetch_full_document`, `summarize_document`, `calculate`, `graph_explore`, `web_search`, `wiki_query` (`tool_executor.go:218-236`) [source].
- **Zero-LLM expansion** (`compiledExpander.Expand`, `tool_compiled_expansion.go:157`): after hybrid search, per bound KB it does a 1-hop expansion per entity kind (knowledge_graph, mind_map, timeline, page_index), the tree structure, three synthesis kinds (wiki_page, artifact_page, essence) and claim neighbours, each capped at 5 to 6 chunks. It then **re-sorts everything with the normal chunks by similarity** [source]. The expansion resolves compiled rows to their **`source_chunk_ids` and loads the raw chunks** (`LoadChunks`). So the context returned to the model is **source chunks with doc id and name**, not entity records.
- **`graph_explore`** (`tool_exploration.go:400`): dense seed search over entity rows (similarity floor 0.8, `kgSeedSim`), ranked by `mention_count_int`, 2 hops (`kgHops`), then an LLM judges whether the subgraph answers; the result is either an answer or chunks [source].
- **Claim recall** (`tool_claims.go`): a KB-wide search of `entity_type_kwd="claim"` rows fused by reciprocal rank, rendering the **verbatim evidence quote up to 1200 chars** with the doc, prefetched into the agent loop (top 6) [source].
- **Provenance.** Chunk and doc ids come through in chunk-shaped results. Entity-level provenance is only via `source_chunk_ids`.
- The classic `KGSearch` ("KG block as one CSV pseudo-chunk") survives only as the legacy path.

### 8. Status
- **Beta?** No "beta" label in the docs I grepped. It is a **new, rapidly changing** feature: introduced in v0.27.0 (2026-08-19), with the rc1 Go rewrite 6 weeks later. rc1's release body lists known issues unrelated to compile (CPU-only DeepDoc, no local sandbox, no Team/Me permission model) [docs].
- **Tests.** 25 `_test.go` files under `knowledge_compiler/` and 217 across `internal/ingestion` and `agentic-rag`, including golden baselines (`golden/fixtures/{structure_wiki,tree}_baseline.json`, `golden/metrics.go`) [source: `find | wc`]. Their results were not run. Tests are against fake engines and fixtures.
- **When to use which** [docs: `overview.md` table]:
  - Graph: people, organizations, products and relationships.
  - Tree: topics and hierarchy.
  - PageIndex: manuals and reports, preserving chapter structure.
  - MindMap: core topics.
  - Timeline: documents with clear time information and events.
  - Wiki: substantial content with relationships between topics.
- The docs' own check list warns to verify "whether relative time is misinterpreted" and "unsupported nodes or edges" for Timeline and Graph [docs: `apply_knowledge_compilation_template.md:74-87`].
- The built-in Graph YAML's entity types (person, org, product, regulation, location, other) and relations (owns, part_of, caused_by, regulates, located_in) are generic. Meeting decisions, campaigns, metric definitions and owners are not modelled [source].

### Verdict (Knowledge Compilation vs classic GraphRAG for our workload)
- **Entity-centric aggregation.** Slightly worse than classic GraphRAG on cross-document linking. Dataset merge is exact-name bucketing, and alias merging through a 0.99 cosine gate rarely fires. Classic GraphRAG at least had a typed candidate blocker plus an LLM confirmation over a looser similarity measure. For Vietnamese neither is adequate, so we build our own alias layer.
- **Temporal and conflicting versions.** Neither supports them. Timeline is a free-text chain with no date type, no anchor date and no validity. Conflicting definitions are either concatenated as text lines (dataset merge) or resolved to the "more recent-looking" value by the LLM (in-doc merge). Flagging the newest needs a dated, per-claim row, which we must design.
- **Verbatim figures and provenance.** Clearly better than classic GraphRAG, which kept only doc ids. Evidence quotes are verified, byte-offset located and tied to chunk ids. But the default Graph and Timeline templates do not ask for evidence, and a payload without evidence passes the gate, so it is opt-in.
- **Incremental edit and delete.** Better for Wiki (hash-keyed chunk cache, diff of contributions). For structure kinds the delete path is cheaper than classic GraphRAG (no global graph rewrite or full community regeneration, just row deletes and source stripping), but stale folded descriptions remain, as before.
- **Relational storage fit.** Good and slightly better: flat rows with kind, name, from and to, source arrays and a JSON payload map straight to Postgres or Delta. The agentic retrieval layer resolves compiled rows back to source chunks, which suits a context-only output.
- **Maturity and cost.** It is new (6 weeks old in rc1), with no published quality data, and the pipeline is LLM-heavy (two calls per batch plus merge judging). It has no community detection, so no global-question summaries beyond Tree and Wiki.
- **Overall.** Do not adopt the model, but **borrow its mechanisms** over classic GraphRAG's: YAML templates, claim rows carrying verified verbatim evidence and chunk ids, doc-level plus merged rows with `source_doc_ids`, content-hash chunk caching and a backlog queue. Our claim row needs what RAGFlow lacks: `valid_from`/`valid_to` or event date, document date, `supersedes`, and an explicit never-merge-conflicts rule.

Gaps: `wiki/` internals beyond state and cache, `mindmap/`, `scheduler.go` and the MySQL scheduling schema were not read. Edit semantics for doc-level rows on re-parse were not traced (stale doc-level rows may be replaced by stable ids). No code run.
